# Design: Deadline Tracker

Computes every immigration-critical deadline from the user's profile with deterministic,
LLM-free formulas, tags each with an urgency tier, tracks the unemployment-day cap, supports
manual overrides, exports to calendar (`.ics`), and sends email reminders.

The deadline **calculations and UI are pure frontend TypeScript**
(`src/utils/deadlineCalculations.ts`, `src/data/deadlineDefinitions.ts`,
`src/utils/computeDeadlines.ts`) with Vitest unit tests. The server-side pieces (the `.ics`
export and the reminder checker) run on Visaroo's FastAPI stack, mirroring the same pure
formulas in Python (`backend/app/deadline_calc.py`).

Unemployment caps are **90 days (OPT) / 150 days (STEM OPT)** per REQ-NF-2; the warning
threshold is "within 30 days of the cap."

## Architecture

All deadline calculations run client-side in pure TypeScript. Nothing server-side is involved
in rendering the list. The only server calls on this page are:
- `PUT /profile` when the user updates unemployment days or a manual date override.
- `GET /deadlines/ics` to download the calendar export.
- `POST /deadlines/remind` to run the reminder checker (used by a schedule/script, not a
  user-facing button).

## Data Model

### Deadline definition (static, code-defined)

```typescript
interface DeadlineDefinition {
  id: DeadlineId;
  label: string;
  description: string;
  consequence: string;
  regulationCite: string;
  officialUrl: string;
  applicableVisaTypes: VisaType[];
  applicablePhases?: string[];           // if null, applies to all phases of the visa type
  calculate: (profile: Profile) => Date | null;
  // returns null if required profile fields are missing
}
```

Definitions are a static array in `src/data/deadlineDefinitions.ts`. Never fetched from an API.
CFR citations and official URLs live here and are never generated by the LLM.

### Computed deadline (runtime)

```typescript
interface ComputedDeadline {
  id: DeadlineId;
  label: string;
  date: Date | null;                     // null = missing profile data
  isOverridden: boolean;
  tier: UrgencyTier;
  daysRemaining: number | null;
  description: string;
  consequence: string;
  regulationCite: string;
  officialUrl: string;
}

type UrgencyTier = 'critical' | 'warning' | 'upcoming' | 'ok' | 'expired' | 'na';
```

### Unemployment counter (derived from profile)

```typescript
interface UnemploymentStatus {
  daysUsed: number;
  cap: number;                           // 90 for OPT, 150 for STEM OPT
  daysRemaining: number;
  percentUsed: number;
  projectedCapDate: Date | null;         // null if eadStartDate missing or daysUsed is 0
  tier: 'ok' | 'warning' | 'critical';
}
```

### Overrides and reminder dedup (stored on existing tables)
- Manual date overrides are stored in a `deadline_overrides` JSON field on the `Profile` row.
- Reminder dedup uses the `reminders_sent` SQLAlchemy table with PK
  `userId#deadlineId#threshold`, so each (user, deadline, threshold) reminder fires at most
  once.

## Deadline Formulas

All implemented in `src/utils/deadlineCalculations.ts` (and mirrored server-side in
`deadline_calc.py` for the `.ics` export and reminders).

```typescript
optWindowOpen        = programEndDate - 90 days
optDeadline          = programEndDate - 60 days
stemOptWindowOpen    = eadEndDate - 90 days
stemOptDeadline      = eadEndDate - 60 days
gracePeriodEnd       = programEndDate + 60 days   // F-1 / OPT
stemGracePeriodEnd   = eadEndDate + 60 days       // STEM OPT
h1bGracePeriodEnd    = i94ExpiryDate + 60 days    // H-1B
sevpDeadline         = lastReportableEventDate + 10 days
unemploymentWarning  = cap - 30 days remaining
projectedCapDate     = eadStartDate + (cap / (daysUsed / daysSinceEadStart)) days
                       // only when daysUsed > 0 and daysSinceEadStart > 0
```

Each function returns `null` when a required source date is missing.

## Urgency Tier Logic

```typescript
function getUrgencyTier(date: Date | null, today: Date): UrgencyTier {
  if (!date) return 'na';
  const days = differenceInCalendarDays(date, today);
  if (days < 0) return 'expired';
  if (days <= 7) return 'critical';
  if (days <= 30) return 'warning';
  if (days <= 90) return 'upcoming';
  return 'ok';
}
```

## Frontend

### Page structure

```
/deadlines
  <DeadlineTrackerPage>
    <PinnedCountdowns />                 // user's pinned live countdowns
    <UnemploymentCounter />              // OPT / STEM OPT only
    <SevpReportingCard />                // F-1 / OPT / STEM OPT only
    <DeadlineList>
      <DeadlineCard />                   // one per applicable deadline
    </DeadlineList>
  </DeadlineTrackerPage>
```

### DeadlineCard
- Collapsed: deadline label, date, days-remaining pill, urgency color indicator.
- Expanded: description, consequence, regulation cite, official link, "Ask about this", and a
  "Pin countdown" action.
- Overridden dates show a small "Overridden" badge with a reset link.
- Missing-data state: grey card with "Complete your profile" link, no date shown.

### UnemploymentCounter
- Progress bar, color-coded by tier.
- Inline number input to update days used; calls `PUT /profile` on blur.
- Projected cap date shown below the bar when calculable.

### SevpReportingCard
- Shows current SEVP status: "No pending report" or a countdown to the deadline.
- "I had a reportable event" opens a date picker; sets the deadline to event date + 10 days.
- "Mark as reported" clears the deadline and logs the report date to the profile.

### Sort order
1. Critical (soonest first)
2. Warning (soonest first)
3. Upcoming (soonest first)
4. OK (soonest first)
5. Expired (most recent first)
6. N/A (hidden by default; "Show non-applicable" toggle)

## Calendar export (`.ics`)

`GET /deadlines/ics` (FastAPI, `routers/deadlines.py`) builds a real RFC-5545 calendar from
the user's computed deadlines (server-side mirror of the same formulas), one `VEVENT` per
deadline, with the "not legal advice" disclaimer in the description.

## Reminders

`services/reminder_checker.py` is the reminder job. It is run by `scripts/send_reminders.py`,
a Kiro hook, or `POST /deadlines/remind` (in production, a daily schedule would call the same
logic):

```
run_reminders(db):
  for each user with notifications.emailEnabled:
    compute all deadlines (deadline_calc.py)
    for each deadline whose days_remaining matches a configured lead-time threshold:
      skip if a reminders_sent row already exists for (user, deadline, threshold)
      send the email via the EmailProvider
      record the reminders_sent row
```

### Email delivery (`EmailProvider`)
Email goes through an env-switched `EmailProvider`:
- `SesProvider` — **Amazon SES** (`EMAIL_PROVIDER=ses`).
- `LocalProvider` — logs an email preview, so reminders work with zero AWS setup
  (`EMAIL_PROVIDER=local`, the default).

### Reminder dedup (`reminders_sent` table)
A single-column SQLAlchemy table with PK `userId#deadlineId#thresholdDays` records that a
reminder was sent, so it fires at most once per (user, deadline, threshold).

### Email template

```

Your {deadlineLabel} is on {date}, {daysRemaining} days from today.

{consequence}
```
